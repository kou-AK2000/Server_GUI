# 共同編集・永続化アーキテクチャ仕様（案）

## 1. 目的

Ordenを、現在のブラウザ内保存・JSON入出力中心のプロトタイプから、組織単位で安全に共有できるアプリケーションへ段階的に発展させるための保存・共有方式を定義します。

本仕様の最重要方針は、**既存のOrden JSONを設計データの正本として維持すること**です。DB導入を理由に、ノード、接続、レベル1〜4の設計情報を無理に多数のテーブルへ分解しません。

## 2. 対象としないもの

- 本仕様は実装計画であり、現時点では未実装である。
- Terraform、CloudFormationなどのIaCとの自動同期は対象外とする。
- 同時編集の導入前に、リアルタイム通信だけを先行実装しない。
- JSON内にパスワード、APIキー、秘密鍵などの秘密情報を保存しない。

## 3. 基本原則

- JSONエクスポート／インポートを継続し、サーバー保存の有無にかかわらず可搬性を保つ。
- JSONには必ず`schemaVersion`を持たせ、アプリ側で旧形式を移行できるようにする。
- PostgreSQLは検索、権限、履歴、共有のために使い、構成図本体は`JSONB`として保存する。
- IndexedDBはローカル下書き、オフライン編集、同期失敗時の退避に使う。ブラウザ保存だけを唯一の正本にしない。
- 組織・案件・構成図の識別子はUUIDを使用し、一度発行したIDを変更しない。
- 共同編集は、実際に同時編集の利用要望が確認されてからYjs（CRDT）で追加する。

## 4. 推奨技術構成

| 領域 | 推奨 | 役割 | 導入時期 |
|---|---|---|---|
| フロントエンド | React + TypeScript | 現行Orden GUI | 継続 |
| ローカル保存 | IndexedDB | 下書き、オフライン、同期キュー | フェーズ1 |
| API | Node.js + TypeScript | 認証、権限、保存、履歴、JSON API | フェーズ2 |
| サーバーDB | PostgreSQL | 組織、権限、一覧、JSON本体、履歴 | フェーズ2 |
| リアルタイム通信 | WebSocket | Yjs更新・在席情報の配信 | フェーズ3 |
| 共同編集 | Yjs | 同時編集時の競合解決 | フェーズ3 |

Yjsは競合を自動統合するCRDTであり、WebSocketなどの通信プロバイダと組み合わせて利用できます。ただし、共同編集のサーバー運用には追加の設計・監視が必要なため、初期のクラウド保存には必須としません。

## 5. 論理アーキテクチャ

```text
利用者のブラウザ
├─ Orden GUI
├─ IndexedDB
│  ├─ ローカル下書き
│  ├─ 未同期変更キュー
│  └─ 直近のサーバー保存版キャッシュ
└─ HTTPS API
   └─ Node.js / TypeScript API
      ├─ 認証・認可
      ├─ プロジェクト／構成図の保存
      ├─ JSONインポート・エクスポート
      └─ 履歴管理
         └─ PostgreSQL

共同編集導入後のみ
ブラウザ ── WebSocket ── Yjs同期サーバー ── PostgreSQL
```

## 6. データモデル

### 6.1 管理用の正規化テーブル

| テーブル | 主な項目 | 役割 |
|---|---|---|
| `users` | `id`, `email`, `display_name` | 利用者 |
| `workspaces` | `id`, `name`, `created_at` | 組織・チームの単位 |
| `workspace_members` | `workspace_id`, `user_id`, `role` | ワークスペース権限 |
| `projects` | `id`, `workspace_id`, `name`, `description` | 案件・システム単位 |
| `diagrams` | `id`, `project_id`, `name`, `document_json`, `schema_version`, `revision` | 構成図と設計データの現在版 |
| `diagram_revisions` | `id`, `diagram_id`, `revision`, `document_json`, `created_by`, `created_at` | 復元可能な履歴 |

`workspaces → projects → diagrams` を管理上の階層とします。現在の「システムを1セットとして保存する」利用感は、まず`project`内に1つの`diagram`を置くことで維持します。将来、ネットワーク図や環境別の構成図を追加しても同じプロジェクト内で管理できます。

### 6.2 Diagramの保存形式

`diagrams.document_json`には、現在JSONエクスポートしている設計データを保存します。

```text
document_json (JSONB)
├─ schemaVersion
├─ projectName
├─ nodes[]
├─ edges[]
├─ systemPolicy
├─ layoutTemplate
└─ その他、Ordenが復元に必要な設計データ
```

DBが内部構造を再構成するのではなく、OrdenのJSONシリアライザ／デシリアライザがJSONを生成・検証・移行します。これにより、次を保証します。

- DB保存した構成図をJSONとして書き出せる。
- 既存JSONをDB保存へ取り込める。
- JSONファイルだけでもバックアップ・移管できる。
- UI項目の追加時は`schemaVersion`ごとの移行関数を追加できる。

### 6.3 JSONの最小メタデータ

JSONエクスポートでは、少なくとも次のメタデータを保持します。

```json
{
  "schemaVersion": "1.0",
  "projectId": "uuid",
  "diagramId": "uuid",
  "exportedAt": "2026-10-26T00:00:00.000Z",
  "document": {}
}
```

サーバー固有の権限情報、アクセストークン、利用者のメールアドレスは、JSONエクスポートに含めません。

## 7. 保存・同期の動作

### 7.1 初期保存

1. 編集内容をIndexedDBへ即時保存する。
2. オンラインかつログイン済みの場合、一定時間の操作停止後にAPIへ保存する。
3. APIは`revision`を確認してPostgreSQLの現在版を更新する。
4. 更新前のJSONを`diagram_revisions`へ保存する。
5. 成功した変更はローカルの未同期キューから削除する。

### 7.2 競合（共同編集導入前）

フェーズ2では同時編集を許可しません。保存時に`revision`が異なる場合は上書きせず、利用者に次を選ばせます。

- 最新版を読み込み、自分の変更を手動で反映する。
- 自分の変更を別の履歴・複製として保存する。

この方式により、Yjsなしでも意図しない上書きを防ぎます。

### 7.3 共同編集（フェーズ3）

共同編集では、1つの`diagramId`を1つのYjsドキュメントとして扱います。

- ノード、エッジ、レベル1〜4の情報をYjsの`Map`／`Array`として管理する。
- 編集中の利用者名・カーソル・選択状態は永続化しない在席情報として扱う。
- 一定間隔または明示保存時に、Yjsの状態をOrden JSONへ変換し、`document_json`と履歴へ保存する。
- JSONインポート時は、現在のYjsドキュメントを置換するのではなく、新しいリビジョンとして検証・反映する。

## 8. 権限

初期ロールは次の3種類とします。

| ロール | 閲覧 | 編集 | 共有設定・削除 |
|---|:---:|:---:|:---:|
| `viewer` | ○ | - | - |
| `editor` | ○ | ○ | - |
| `owner` | ○ | ○ | ○ |

APIでは、すべての`projectId`／`diagramId`アクセス時にワークスペース所属とロールを検証します。WebSocket導入後も、接続時に同じ認可を必須とします。

## 9. 実装フェーズ

### フェーズ0：JSON契約の固定

- 現在のJSONに`schemaVersion`を明示する。
- import時に形式を検証し、旧版から最新版へ移行する関数を用意する。
- JSONの入出力・復元を自動テストする。

### フェーズ1：IndexedDBへの移行

- 現行ブラウザ保存をIndexedDBベースに変更する。
- プロジェクト一覧、最終更新日時、ローカル下書きを保持する。
- JSONファイル入出力は継続する。

### フェーズ2：クラウド保存・履歴・権限

- Node.js API、PostgreSQL、認証を導入する。
- `document_json`（JSONB）による保存と、`diagram_revisions`による履歴を実装する。
- 共同編集は行わず、リビジョン競合を検出する。

### フェーズ3：Yjs共同編集

- WebSocketとYjsを導入する。
- 同一構成図の複数人編集、在席表示、競合なし統合を実装する。
- 共同編集・切断復帰・履歴復元の負荷試験を行う。

## 10. 完了条件

フェーズ2完了時点で、次を満たすことを目標とします。

- ログインした利用者がワークスペースとプロジェクトを作成できる。
- 権限に応じて構成図を閲覧・編集できる。
- 現在のOrden JSONをインポートし、同じ表示・設計情報として復元できる。
- サーバー保存した構成図をJSONとしてエクスポートできる。
- 直近の履歴から任意の版を復元できる。
- 通信失敗時も編集内容がIndexedDBへ退避される。
- 秘密情報がJSON、DBログ、履歴に保存されない。
