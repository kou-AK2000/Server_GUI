# 本番公開に向けた改善・セキュリティロードマップ

## 目的

Ordenをローカル検証用プロトタイプから、機密性を持つインフラ設計情報を組織で扱えるサービスへ発展させるために、現在実装する改善と本番公開前に必須となる要件を分けて管理します。

## 1. 現時点で実装するもの

### UI用語とファイル操作

- メニュー名を「書き出し」から「エクスポート」へ変更する。
- 「JSONを開く」を「JSONからインポート」へ変更する。
- Fileメニュー内へ、インポートとエクスポートのサブメニューを集約する。
- エクスポート対象はJSON、CSV、Excelとする。

### IndexedDBの役割

IndexedDBは正式な共有データの保存先ではなく、編集中の一時保存、オフライン時・通信失敗時の退避、直近の作業状態のキャッシュに限定します。

画面上では「このブラウザ内の一時保存」と明示し、正式な保存・共有にはクラウド保存またはJSONエクスポートを使うよう案内します。

### 正式な保存先

PostgreSQLを正式データの保存先とします。構成図・レベル1〜4の設計情報は既存のOrden JSON形式を維持し、`JSONB`として保存します。DBはWorkspace、Project、Diagram、権限、リビジョン履歴を管理します。

## 2. 現在の開発環境における制約

- `ORDEN_DEV_AUTH=true`と開発用HTTPヘッダーはローカル検証専用であり、公開環境では使用しない。
- IndexedDB・ローカルPostgreSQLに、秘密鍵、パスワード、APIトークンなどの秘密情報を保存しない。
- Docker ComposeのDBパスワードはローカル開発専用である。
- 実在する顧客情報・本番IPアドレスなどの機密データを使った共有検証は、本番セキュリティ実装後に行う。

## 3. 本番公開前に必須の実装

### 認証・認可

- OIDCまたは社内SSOによる正式ログイン
- Workspaceごとの`owner`、`editor`、`viewer`管理
- メンバー招待、削除、ロール変更の管理画面
- API・将来のWebSocket接続ごとのサーバー側認可

### 通信・Webアプリケーションの保護

- HTTPS/TLSへの統一とHTTPからのリダイレクト
- セキュアなCookie／セッション管理
- 本番用に固定したCORS許可オリジン
- Content Security Policy（CSP）、XSS対策、依存パッケージの脆弱性確認
- APIログへ設計データ・認証情報を出力しない

### データ保護・復旧

- DBストレージとバックアップの暗号化
- DBバックアップ、復元手順、復元訓練、保持期間の定義
- DB・APIの最小権限化とSecret Manager等による秘密情報管理
- 閲覧・更新・共有設定変更を追跡する操作監査ログ

アプリケーション内部の項目単位暗号化は、規制・顧客要件・脅威モデルに基づき必要性を判断して追加します。IndexedDBだけを一般的に暗号化しても、同一オリジンで動く悪意あるJavaScriptへの根本対策にはなりません。

## 4. サーバー側検索

検索はブラウザのIndexedDBではなく、認可済みのPostgreSQL側で実行します。

- Workspace・Project・構成図名
- 部品名、ホスト名、IPアドレス
- OS、配置形態、クラウド・仮想化基盤
- ミドルウェア名、バージョン、ポート

検索では必ずWorkspace権限を先に検証します。`JSONB`のインデックスと、一覧表示用の正規化メタデータを必要に応じて併用します。

## 5. 実装順序

1. UI文言・Fileメニューの整理、ブラウザ保存の注意表示
2. 正式認証とWorkspaceメンバー管理
3. HTTPS、バックアップ、監査、運用監視
4. サーバー側検索
5. Phase 3の共同編集（Yjs／WebSocket）

## 6. 本番公開の完了基準

- 正式ログインを使い、権限のないWorkspace・Project・Diagramを取得できない。
- HTTPS以外で設計データ・認証情報を通信しない。
- DBのバックアップから構成図と履歴を復元できる。
- 操作監査ログから、誰がいつ何を変更したかを追跡できる。
- IndexedDBは一時保存であることがUI・操作説明に明示されている。
